# Android Bouncy Castle dependency refresh

The Android image profile refreshes the official command-line tools' Bouncy Castle closure before collecting the SBOM. This is a dependency fix, not a vulnerability exception. The measured vendor bundle contained BC 1.80.2; the two observed High/Critical provider advisories list 1.85 as fixed. On 2026-11-11, Maven Central's current stable release for all three artifacts was 1.86.

After installing the SDK and build tools, [refresh-android-bc.py](image/refresh-android-bc.py) resolves matching stable `bcprov-jdk18on`, `bcpkix-jdk18on` and `bcutil-jdk18on` releases from the official `org/bouncycastle` Maven Central metadata. Each downloaded JAR must match its official SHA256 and manifest version. Mixed releases, preview versions, invalid checksums, missing/ambiguous packages and paths escaping the tools root fail the build.

The helper installs official JAR bytes under their real new version directories and filenames. It updates only the references in the SDK's unsigned metadata-only classpath JARs, preserving their other entries, including the vendor stamp. Unknown classpath archive contents require review instead of silently rewriting executable or signed archives. The SDK bundle revision remains unchanged; this is a locally remediated dependency set, not an assertion that Google's original archive contained the new libraries.

The old JARs remain available until the candidate passes activation checks, then are retired so stale vulnerable copies do not remain in the image. Failure restores original dependency/classpath bytes and modes and the previous receipt, or removes a newly created success receipt. Candidate paths are checked before writing. The helper does not modify Kotlin compiler archives, other Java libraries or the official Actions runner.

## Verification and evidence

The actual Java consumer probe checks the provider version and the code origin of classes from all three installed JARs. It generates a key and certificate, roundtrips a PKCS12 keystore, rejects a wrong password, signs/verifies CMS content and rejects modified content. The actual SDK `apkanalyzer files list` command must enumerate a synthetic APK's manifest and asset. This APK check exercises archive enumeration, not a compiled/signed application or the complete Android build/deploy lifecycle.

The receipt is `lib/runner-images-bc.json` inside the selected command-line-tools directory. It records the resolved official URLs, versions and SHA256 values, the exact installed dependency and classpath JAR hashes, and consumer observations. Independent `verify` rejects changed files, duplicate JARs, stale classpath references, altered receipts and a release predating the known 1.85 fixes; it repeats the real consumer checks. Unchanged refresh replay verifies the installed state without redownloading JARs.

The image builder performs refresh after SDK installation and independent verification under the job environment before SBOM collection. Its native-check output includes the dependency receipt and its SHA256, bound by the existing qualification evidence hash. The helper source participates in the Mac recipe fingerprint. Live Maven metadata is resolved when an Android build runs; a Maven-only release does not independently schedule a Mac rebuild.

Local behavioral tests isolate network/JVM boundaries and exercise integrity failures, activation and post-retirement rollback, replay, tampering, mixed/preview releases and path ownership. The lifecycle test requires a failed refresh or independent verification to stop image qualification and remove only the generated image.

An isolated copy of the checksum-verified official Android tools 23.0 archive plus official build tools 37.0.0 passed the actual native Java/APK checks with BC 1.86. A real Java provider-version mismatch rejected activation and restored the original files and modes. Syft identified exactly the three 1.86 JAR packages at their new paths; Grype found zero vulnerabilities and zero ignored matches for that component. This is component validation on the local Mac, not a fresh factory VM/image qualification. The existing whole-image SBOM still describes the earlier BC 1.80.2 installation and cannot be treated as updated by this component result.
